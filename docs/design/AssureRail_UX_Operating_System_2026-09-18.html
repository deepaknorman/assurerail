AssureRail UX Operating System

A functional, intuitive product comes from one set of interaction rules enforced in code and tested through complete user journeys. Every release must prove the customer can understand where they are, complete the next task, recover from errors and trust what the system saved.

The operating model

1 Define the golden journey→2 Build from shared primitives→3 Test desktop and mobile→4 Observe pilot friction→5 Block regressions
5 statesEvery data screen explicitly handles idle, loading, ready, empty and error.
1 scopeCustomer data and pending actions are bound to the active institution and cleared on a scope change.
1 next stepEach page explains the task, prerequisite and outcome beside the action that needs it.
0 raw errorsTechnical details remain in controlled logs; customers receive safe, actionable language.

Release gate

  1. Source gate: no raw technical errors, direct exception messages or inaccessible shared feedback.
  2. Build gate: TypeScript and production build pass for the touched workspace.
  3. Golden-path gate: authorised synthetic accounts complete critical journeys on desktop Chromium and mobile WebKit.
  4. Interaction audit: one visible page heading, labelled controls, named actions, no duplicate IDs and no horizontal overflow.
  5. State-transition audit: institution, engagement, document-version and sign-in mode changes cannot expose or act on stale state.
  6. Security gate: daily offline security harness passes and authenticated browser evidence excludes credentials, traces and screenshots.

Release commands: npm run ux:source, npm run ux:e2e:list, and—only against an authorised synthetic environment—npm run ux:e2e.

Definition of done for every customer screen

Comprehension

  • One clear page purpose and primary action.
  • Plain labels; complex terms have contextual help.
  • Commercial consequences appear before acceptance.

Control

  • Edits clear obsolete success, error and selection state.
  • Destructive or governed actions state prerequisites.
  • Retry does not duplicate a saved request.

Accessibility

  • Keyboard-complete journey and visible focus.
  • Semantic form, heading and disclosure structure.
  • Errors are announced and connected to recovery.

Trust

  • Loading, empty and failure states are distinct.
  • Institution data never survives a scope switch.
  • Saved outcome and next step are explicit.

Pilot feedback without repeated founder review

Run five observed seller sessions against the synthetic EV cohort. Record task completion, time, backtracks, validation failures and support requests by journey step. Review the aggregate after every session and fix any blocker before the next participant. Product analytics must use event names and opaque record identifiers only; document contents, loan data, authentication secrets and personal data stay out of telemetry.

Release owner: engineering proves the automated gate; product signs off the journey copy and commercial consequences; security signs off scope isolation and evidence handling. A screen that fails a golden journey does not ship.
